# Universe At War — Plan d'implémentation Milestones 3 → 10

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Préparer l'implémentation des jalons restants sur le socle M0–M2 : feuille de route M3→M10 avec décisions transverses, puis plans TDD détaillés pour le socle transverse et les Milestones 3, 4 et 5 (recherche/chantier, moteur de flotte, espionnage/combat/débris). Les Milestones 6 à 10 seront détaillés au démarrage de chacun, sur la base de la feuille de route et de leurs briefs.

**Architecture:** Monolithe modulaire Go : `internal/domain` (règles pures, stdlib seulement) → `internal/app` (cas d'usage, frontières transactionnelles, ports côté consommateur) → `internal/storage/sqlite` (une transaction d'écriture par commande, événements planifiés idempotents) → `internal/web` (SSR `html/template`, PRG, CSRF, aucune formule). Le temps est piloté par `scheduled_events` traités par un worker sans boucle active. L'IA (M8–M9) n'appelle que les cas d'usage de `internal/app`.

**Tech Stack:** Go 1.27, `database/sql` + `modernc.org/sqlite` (sans CGO), `net/http` (ServeMux 1.22), `html/template`, `embed`, `log/slog`, `golang.org/x/crypto/argon2`, `math/rand/v2` (PCG seedé) pour le hasard déterministe. Aucune nouvelle dépendance prévue.

**Spec:** `SPECIFICATION_OGAME_LOCAL_GO.md` (source de vérité), `MILESTONE_03…10_*.md` (briefs par jalon), `docs/architecture/*.md`, `docs/rules/economy.md`, `docs/rules/building-costs.md`.

## Contexte

Le dépôt contient un socle livré et vert (build, `go test ./...`, race, vet, staticcheck, govulncheck, cross-builds) couvrant les milestones 0, 1 et 2 : migrations embarquées `0001`–`0004`, bootstrap administrateur, authentification Argon2id + sessions opaques, assistant de configuration en 10 étapes, ruleset versionné, économie paresseuse (production, stockage, énergie), catalogue de bâtiments, file de construction et worker d'événements. Huit briefs de jalon (`MILESTONE_03` à `MILESTONE_10`) décrivent le reste à haut niveau, sans découpage technique.

Ce plan transforme ces briefs en tâches exécutables. Il commence par un **socle transverse** (Partie 0) : quatre limites du code actuel bloquent mécaniquement le M3 (worker mono-type, ruleset non évolutif, projections mono-planète, absence de layout HTML). Puis les Milestones 3, 4 et 5 sont décomposés en tâches TDD avec fichiers, interfaces, tests et commits. Les Milestones 6 à 10 sont cadrés par la feuille de route (décisions D1–D10, dépendances, scénarios) et seront détaillés à leur tour, une fois M5 livré, car leur conception dépend des interfaces réellement stabilisées par M3–M5.

Après validation, ce document est scindé dans `docs/plans/` (une feuille de route + un fichier par partie) : c'est la première tâche d'exécution (Partie 0, tâche F0).

## Contraintes globales (copiées de la spécification)

- Go 1.27.x ou plus récent ; `database/sql` ; driver `modernc.org/sqlite` ; aucun CGO ; un seul binaire ; aucun service externe.
- Monolithe modulaire ; aucune logique métier dans les handlers HTTP ni en JavaScript ; le domaine ignore HTTP, templates, cookies, SQLite, chemins de fichiers.
- TDD strict : test rouge → implémentation minimale → test vert → refactor. Aucune fonctionnalité métier sans tests.
- CI verte : `gofmt`, `go test ./...`, `go test -race ./...`, `go vet ./...`, `staticcheck`, `govulncheck`, builds linux/amd64, linux/arm64, windows/amd64, darwin/amd64, darwin/arm64 (`CGO_ENABLED=0`).
- Timestamps stockés en UTC (`RFC3339Nano`, précision seconde pour les instants de jeu) ; tables `STRICT` ; FK, UNIQUE, CHECK explicites.
- Toute action métier = une transaction SQLite unique ; jamais de rendu ni de réseau dans une transaction.
- Événements planifiés : ordre `(due_at, priority, id)`, clé d'idempotence unique, état terminal = no-op au rejeu ; version de ruleset capturée pour la non-rétroactivité.
- Le domaine n'appelle jamais `time.Now()` ni une RNG globale ; horloge et seed injectées.
- Identifiants persistés en `snake_case`, jamais des libellés traduits ; textes UI en français dans la couche web uniquement.
- Vérité serveur ≠ connaissance joueur : jamais d'information cachée envoyée puis masquée en CSS.
- L'IA passe exclusivement par les cas d'usage joueurs ; aucune API interne « triche ».
- Commits petits en anglais conventionnel (`feat:`, `docs:`, `test:`, `refactor:`, `perf:`), chaque tranche compilable et verte.
- Avant chaque grand système, une fiche `docs/rules/<système>.md` (comportement, formule, constantes, exemples, cas limites, tests de référence). Aucune approximation silencieuse : incertitude documentée → règle explicite → configurable → testée.

### Limites du code actuel qui bloquent le M3 (traitées en Partie 0)

1. **Worker mono-type.** `EconomyRepository.NextDue`/`completeOne` filtrent `event_type = 'building_completed'` ; `Worker` n'accepte qu'un `Processor`. Dès le M3 il faut `research_completed` et `production_completed`, puis une dizaine de types.
2. **Ruleset non évolutif.** `rules.Decode` utilise `DisallowUnknownFields` et `Validate()` rejette les zéros ; tout nouveau champ (M3 : `catalogue_version`, M4 : carburant, M5 : espionnage…) rendrait indécodables les documents `ruleset_versions` déjà persistés.
3. **Projection mono-planète.** `scanAndSettlePlanet` fait `ORDER BY p.id LIMIT 1` ; les routes `POST /planets/{planet}/…` existent mais `GET /` ne sait afficher qu'une planète. Le réseau de recherche (M3) et la colonisation (M6) exigent la liste des planètes d'un joueur et une sélection explicite.
4. **Pas de layout HTML.** Chaque template est un document complet sans navigation ; cinq pages arrivent au M3, une quinzaine ensuite.
5. **Observabilité non câblée.** `observability.NewLogger` n'est appelé nulle part ; aucune corrélation `request_id`, aucune métrique.
6. **Aucun parcours d'inscription.** Seul l'administrateur bootstrap existe ; les tests insèrent des comptes en SQL. Le brief M10 place les inscriptions en fin de projet, mais le critère « chaque jalon livre une version jouable » et les scénarios à deux joueurs (M5, M7) imposent un compte joueur créable sans SQL. Décision : une inscription **minimale** (politique `closed`/`open` déjà présente dans `Identity.RegistrationPolicy`) entre en Partie 0 ; invitations, limitation d'abus et messages anti-énumération restent au M10.

## Décisions transverses

Ces décisions s'appliquent à tous les jalons. Toute déviation exige un ADR dans `docs/adr/`.

### D1 — Dispatch des événements par type

- Nouveau `internal/storage/sqlite/events.go` : `EventProcessor` sélectionne **le prochain événement dû quel que soit son type** (`WHERE state='pending' AND due_at <= ? AND attempts < 5 ORDER BY due_at, priority, id LIMIT 1`) dans une transaction d'écriture, puis délègue à un `EventHandler` enregistré par `event_type`, **dans la même transaction**. Le handler renvoie `nil` → l'événement passe à `completed` et la transaction est validée ; erreur → rollback, puis dans une transaction courte séparée `attempts = attempts + 1, last_error = ?`. Un type inconnu est traité comme une erreur (l'événement reste visible dans le dashboard admin du M10).
- `EventProcessor` implémente `simulation.Processor` (`CompleteDue`, `NextDue` global). `Worker` ne change pas.
- Chaque repository expose `RegisterHandlers(*EventProcessor)`. Le handler `building_completed` actuel est migré à l'identique.
- Table des priorités (documentée dans `docs/architecture/scheduled-events.md`, valeur plus petite = traité en premier à échéance égale) :

| event_type | priorité | jalon |
| --- | ---: | --- |
| `combat_resolved` (arrivée d'attaque / ACS) | 10 | M5/M7 |
| `espionage_resolved` | 20 | M5 |
| `fleet_arrived` (transport, stationnement, colonisation, recyclage, expédition) | 30 | M4 |
| `fleet_returned` | 40 | M4 |
| `building_completed` | 50 | M2 |
| `research_completed` | 60 | M3 |
| `production_completed` | 70 | M3 |
| `holding_ended`, `acs_locked`, `jump_gate_ready` | 80 | M4/M6/M7 |
| `ai_think` | 90 | M8 |
| `protection_expired`, `ban_expired`, entretien | 100 | M10 |

  Justification : à échéance identique, un combat doit être résolu avant qu'une flotte défensive ne « revienne » ou qu'une production ne livre des unités ; l'IA réfléchit après que le monde a changé.

### D2 — Frontière transactionnelle

- Style conservé : un repository = des méthodes qui ouvrent chacune **une** transaction d'écriture. Ajout d'un helper unique `withWriteTx(ctx, db, func(*sql.Tx) error) error` dans `internal/storage/sqlite/tx.go` pour supprimer le boilerplate `BeginTx/Rollback/Commit`.
- Les fonctions internes prennent `*sql.Tx` (comme `loadPlanetByID`, `persistProduction`) et sont réutilisées par les handlers d'événements.
- Les ports restent déclarés côté consommateur (`internal/app/<usecase>/service.go`).

### D3 — Évolution du ruleset sans migration de documents

- `rules.Decode` décode **par-dessus `Default()`** : un document ancien garde les valeurs par défaut des sections absentes ; `DisallowUnknownFields` est conservé (un document d'une version future est refusé). Ajout de `SchemaVersion int` (`schema_version`, valeur courante `2` au M3, incrémentée à chaque ajout de section).
- Les nouveaux réglages de jeu vont dans des sections dédiées : `Progression.CatalogueVersion string` (M3), `Fleet FleetSettings` (M4), `Espionage EspionageSettings` (M5), `Expansion ExpansionSettings` (M6), `Expedition ExpeditionSettings` (M10). `Validate()` est étendu à chaque fois ; le wizard (`setup_form.go`) expose les champs de la section correspondante.
- Les catalogues (bâtiments, recherches, unités, rapid fire, table d'expédition) sont **définis en Go** dans `internal/domain/<x>` et identifiés par `Progression.CatalogueVersion` (`"classic-1"`). Un validateur unique `rules.ValidateWithCatalogue(r, catalogue)` vérifie les identifiants et le graphe de prérequis à l'activation (wizard, import, administration).

### D4 — Multi-planètes et navigation

- `EconomyRepository.Planets(ctx, accountID, now)` renvoie les corps (planètes puis lunes au M6) du joueur, réglés paresseusement. `GET /` devient la **vue globale** (empire : corps, ressources, files, flottes, événements proches). `GET /planets/{planet}` est la page planète actuelle. Toutes les pages de jeu prennent `{planet}` dans l'URL ; le layout affiche un sélecteur de corps.
- Le contrôle de propriété (`planet.owner_player_id ↔ players.account_id`) est fait **dans la transaction** par chaque repository, jamais dans le handler.

### D5 — Layout et rendu

- `web/templates/layout.html` définit `{{define "layout"}}` (head, header avec navigation et sélecteur de corps, `{{template "content" .}}`, footer avec horodatage serveur). Chaque page définit `{{define "title"}}` et `{{define "content"}}`. `webhandler.New` construit **un `*template.Template` par page** par clonage du layout (`layout.Clone()` puis `ParseFS(page)`), ce qui autorise le même nom `content` dans chaque fichier.
- Un seul fichier `web/static/app.css` (design tokens en custom properties) et un seul `web/static/app.js` (countdowns décoratifs, confirmations, SSE au M10), servi sous CSP `default-src 'self'` sans inline.
- Données de page : une struct `pageShell{CSRFToken, Error, Principal, Bodies []bodyLink, Current *bodyLink, Now time.Time}` embarquée par chaque `xxxPageData`.

### D6 — Hasard déterministe

- `internal/domain/random` : `type Source interface{ Float64() float64; IntN(n int) int }` et `func NewSeeded(seed uint64) Source` basé sur `math/rand/v2` `PCG(seed, 0xda3e39cb94b95bdb)`. Les seeds sont tirées avec `crypto/rand` au moment de la création de la mission/tentative et **persistées** (`fleets.seed`, `combat_reports.seed`, `expedition_reports.seed`). Le domaine ne reçoit jamais autre chose qu'une `Source`.

### D7 — Rapports et connaissance

- Table unique `reports` (M5) : `id, recipient_player_id, kind, subject_type, subject_id, coordinate, occurred_at, read_at, payload_version, payload json, shared_alliance_id, created_at`. Le **payload est filtré à la création** selon les droits du destinataire ; il n'existe aucun rapport « complet » à masquer ensuite. Un rapport partagé (M7) est référencé, jamais copié.
- Les projections joueur (`internal/app/.../view.go`) sont des structs distinctes des agrégats ; une projection ne contient que ce que le joueur a le droit de voir. Le test structurel du M8 (`tests/ai_isolation_test.go`) vérifie que `internal/ai` n'importe aucun repository de vérité.

### D8 — Identité joueur

- `players.id` est la clé de tout état de jeu (recherches, flottes, rapports, alliances). Les repositories résolvent `player_id` depuis `account_id` dans la transaction (`playerByAccount(ctx, tx, accountID)`), et refusent `ErrNoEmpire` sinon. Les IA (M8) sont des lignes `players` avec `kind='ai'` et **sans compte** (`account_id NULL` après migration `0010`).

### D9 — Observabilité minimale dès la Partie 0

- `serve` crée le `slog.Logger` (`observability.NewLogger(os.Stderr, config.LogLevel)`), un middleware `requestID` (16 octets `crypto/rand` en hex, header `X-Request-Id`, valeur dans le contexte), journalise chaque requête (méthode, chemin, statut, durée, request_id, account_id si connu) et chaque erreur du worker (event_id, event_type, tentative). Jamais de token, mot de passe, hash ni cookie dans les logs. Les métriques (compteurs internes) arrivent au M10.

### D10 — Organisation des paquets

- On garde `internal/app/simulation` (pas de déplacement cosmétique vers `internal/sim`). Nouveaux paquets domaine : `research`, `unit`, `fleet`, `espionage`, `combat`, `debris`, `moon`, `alliance`, `acs`, `expedition`, `random`, `report`, `intelligence`. Nouveaux paquets application : `research`, `shipyard`, `fleet`, `espionage`, `combat` (résolution), `expansion`, `alliance`, `acs`, `registration`, `administration` (existant, étendu), `moderation`, `reports`. L'IA vit dans `internal/ai` (M8–M9) et n'importe que `internal/app/*` et `internal/domain/*`.
